# BrevitySisterBot 0.2.0: production-архитектура на Beget

## 1. Статус и назначение

Этот документ описывает согласованную архитектуру новой версии
BrevitySisterBot `0.2.0`.

Текущая реализация считается MVP-версией `0.1.0`. При реализации нового
проекта она будет перенесена в каталог `mvp-1/` без изменения поведения.
Корень репозитория после этого займёт новое приложение `0.2.0`.

Версия `0.2.0` создаётся как чистая переработка, а не как постепенное
расширение старого кода. Это оправдано тем, что production-контур меняется
принципиально:

- Telegram long polling заменяется webhook;
- локальные SQLite-базы заменяются MySQL;
- локальная цепочка cron-команд заменяется событийной обработкой с recovery- и
  плановыми задачами Beget;
- локальная модель Ollama заменяется внешней моделью Groq;
- добавляются личные запросы сводок и выбор группы.

Целевой масштаб — до 20 Telegram-групп. Начальная реальная нагрузка — две
группы, при этом живые данные сейчас есть только у одной группы.

## 2. Поведение продукта

### 2.1 Сбор сообщений из групп

Бот получает каждый Telegram update через HTTPS webhook. Сообщение группы
сохраняется в MySQL непосредственно во время webhook-запроса. Периодического
сбора сообщений и отставания на пять минут больше нет.

Бот отслеживает только группы, которые были подключены командой
`/enable_daily`. Отключение ежедневной публикации останавливает плановые
сводки, но не удаляет настройки группы и накопленные связи с участниками.

Команды `/enable_daily` и `/disable_daily` доступны только текущему
администратору группы. Права проверяются через Telegram `getChatMember`.

### 2.2 Плановая вечерняя сводка

В версии `0.2.0` все группы используют одно расписание в часовом поясе
`Europe/Moscow`:

- в `20:45` начинается финальная подготовка;
- в `21:00` сводка публикуется.

Автоматическая сводка генерируется только при наличии минимум 15 подходящих
сообщений за текущий день. Если сообщений меньше, бот не обращается к LLM и
ничего автоматически не публикует.

Индивидуальное время публикации для каждой группы не входит в версию `0.2.0`.

### 2.3 Сводка по запросу внутри группы

Любой текущий участник подключённой группы может вызвать `/summary` в группе.
Ответ увидят все участники этой группы.

Для ручной сводки требуется минимум пять подходящих сообщений. Если сообщений
меньше пяти, бот сообщает, что материала для содержательной сводки пока
недостаточно.

Если для того же набора исходных сообщений уже существует подходящая сводка,
бот может вернуть её из кеша. Иначе он создаёт новую сводку по всем сообщениям,
которые были сохранены к моменту запроса.

Ручная сводка не должна перезаписывать или преждевременно публиковать плановую
сводку на 21:00.

### 2.4 Личная сводка

Пользователь может вызвать `/summary` в личном чате с ботом.

Бот хранит связи между Telegram-пользователями и подключёнными группами на
основании сообщений и команд, которые он видел в этих группах. Для первичной
привязки пользователь должен хотя бы один раз вызвать `/summary` внутри нужной
группы.

Перед выдачей данных в личном чате бот проверяет текущее членство пользователя
через Telegram `getChatMember`. Проверка выполняется для каждого личного
запроса или callback выбора группы:

- если доступна одна подключённая группа, бот сразу присылает её сводку;
- если доступно несколько групп, бот показывает inline-кнопки выбора;
- если текущее членство подтвердить нельзя, данные группы не выдаются.

Личный запрос и его результат не появляются в группе.

### 2.5 Сообщение о времени обработки

Перед операцией, которой может понадобиться LLM, бот сразу отправляет:

> Запрос принят. Подготовка может занять до 1–2 минут. Пожалуйста, не
> отправляйте команду повторно.

Если тот же пользователь повторяет эквивалентный запрос, пока первый ещё
выполняется, новая генерация не создаётся. Бот сообщает, что сводка уже
готовится.

Штатная обработка начинается во время webhook-запроса и обычно должна
завершаться за несколько секунд. Cron раз в пять минут служит гарантией
восстановления, а не обычным временем ответа.

## 3. Выбранная архитектура размещения

### 3.1 Ограничение по хостингу

BrevitySisterBot и BernsBot размещаются на обычном виртуальном хостинге Beget.
VPS, постоянно работающий polling-процесс, Docker Compose и отдельный серверный
брокер сообщений не требуются.

У приложений могут быть общие эксплуатационные стандарты, но сами приложения
строго изолированы:

- разные домены или поддомены;
- разные каталоги размещения;
- разные Telegram bot tokens;
- разные webhook secret tokens;
- разные MySQL-базы;
- разные `.env`, логи, backup и preview-контуры.

Ни один бот не должен читать или изменять production-базу другого бота.

### 3.2 Runtime-компоненты

Приложение `0.2.0` состоит из следующих частей.

#### 1. WSGI webhook-приложение

- работает через Passenger;
- принимает только Telegram `POST`-запросы;
- проверяет `X-Telegram-Bot-Api-Secret-Token`;
- сохраняет update до начала бизнес-обработки;
- пытается обработать update сразу;
- возвращает успешный webhook-ответ без постоянно работающего процесса.

#### 2. Обработчик updates

- идемпотентно захватывает задания из очереди;
- обрабатывает команды, сообщения, сведения об участниках и callbacks;
- сохраняет состояние, количество попыток и ошибки;
- безопасно повторяет прерванную работу.

#### 3. Сервис суммаризации

- читает сообщения группы за нужный временной интервал;
- формирует ограниченный transcript;
- обращается к настроенному LLM-провайдеру;
- проверяет и нормализует структурированный ответ;
- при необходимости делает не более одного repair-запроса;
- при неудаче использует существующий детерминированный эвристический fallback.

#### 4. Telegram-клиент

- отправляет подтверждения, результаты, ошибки и кнопки выбора группы;
- проверяет администраторов и текущее членство;
- безопасно повторяет Telegram-операции без двойной публикации.

#### 5. Recovery worker

- запускается через Beget CronTab каждые пять минут;
- подбирает ожидающие, повторяемые и зависшие задания;
- не перечитывает Telegram и не собирает сообщения;
- быстро завершается, если очередь пуста.

#### 6. Плановые команды

- готовят вечерние сводки;
- публикуют подготовленные сводки;
- архивируют завершённый день;
- очищают только безопасно архивированные рабочие данные;
- удаляют просроченные архивные строки;
- создают и ротируют backup;
- выполняют ежедневную эксплуатационную проверку.

### 3.3 Почему выбран этот подход

Рассматривались три варианта:

1. **Python WSGI webhook, MySQL, немедленная обработка и recovery cron раз в
   пять минут** — выбранный вариант. Бизнес-логика остаётся на Python,
   сообщения записываются без задержки, а схема совместима с виртуальным
   хостингом Beget.
2. **PHP webhook и обработка Python по cron** — допустимо, но создаёт обычную
   задержку очереди и дополнительную границу между двумя runtime.
3. **Полная реализация на PHP** — соответствует текущему production-подходу
   BernsBot, но потребует заменить или продублировать зрелый Python-суммаризатор.

В выбранной схеме cron используется только для восстановления и точных
плановых операций.

## 4. Модель данных

Для BrevitySisterBot используется одна физическая MySQL-база. Рабочие и
архивные данные разделяются таблицами, а не отдельными базами.

### 4.1 Основные таблицы

#### `telegram_updates`

Надёжный webhook inbox и очередь обработки.

Основные поля:

- `update_id` — Telegram update ID и уникальный ключ;
- `payload_json` — исходный update для повторной обработки;
- `status` — `pending`, `processing`, `completed`, `retry` или `failed`;
- `attempt_count`;
- `available_at`;
- `claimed_at`;
- `completed_at`;
- `last_error_code`;
- `last_error_message`;
- `created_at`.

Повторная доставка update допускается, но не создаёт повторную работу.

#### `tracked_chats`

Настройки групп.

Основные поля:

- `chat_id` — Telegram chat ID и первичный ключ;
- `title`;
- `enabled`;
- `timezone`, вначале всегда `Europe/Moscow`;
- `scheduled_publish_time`, вначале всегда `21:00`;
- `created_at`;
- `updated_at`.

#### `chat_members`

Наблюдаемые связи пользователей с группами, необходимые для поиска групп при
личном запросе.

Основные поля:

- `chat_id`;
- `user_id`;
- отображаемые сведения о пользователе;
- `first_seen_at`;
- `last_seen_at`;
- `last_membership_check_at`;
- `last_membership_status`.

Эта таблица используется только для поиска возможных групп и не является
источником авторизации. Перед личной выдачей бот всегда заново проверяет
Telegram-членство для текущего запроса или callback выбора.

#### `messages`

Временные рабочие сообщения.

Основные поля:

- внутренний ID;
- `chat_id`;
- `telegram_message_id`;
- сведения об отправителе;
- текст;
- `sent_at`;
- `created_at`.

Уникальный ключ: `(chat_id, telegram_message_id)`.

#### `prepared_summaries`

Сгенерированные сводки и их жизненный цикл.

Основные поля:

- внутренний ID;
- `chat_id`;
- `summary_date`;
- `summary_kind` — `scheduled` или `on_demand`;
- `requester_user_id`, пустой для плановой сводки;
- watermark исходных сообщений и детерминированный source hash;
- текст сводки;
- `status` — `preparing`, `prepared`, `sending`, `sent`, `retry` или `failed`;
- provider, model, latency, число токенов или символов и тип fallback;
- `prepared_at`;
- `sent_at`;
- сведения об ошибках.

Плановая сводка имеет уникальную логическую идентичность
`(chat_id, summary_date, summary_kind)`.

Ручные сводки дедуплицируются и кешируются по
`(chat_id, summary_date, summary_kind, source_hash)`. Пользователь-инициатор
сохраняется для доставки и аудита, но не вынуждает делать второй LLM-запрос для
того же состояния чата.

#### `scheduled_publications`

Идемпотентный outbox плановых публикаций.

Основные поля:

- `chat_id`;
- `summary_date`;
- ID подготовленной сводки;
- `status`;
- `attempt_count`;
- метаданные результата Telegram;
- `sent_at`.

Уникальный ключ `(chat_id, summary_date)` не позволяет дважды опубликовать
сводку на 21:00.

#### `archived_messages`

Тридцатидневная копия сообщений успешно завершённых дней.

Уникальный ключ сохраняется: `(chat_id, telegram_message_id)`.

#### `archived_summaries`

Тридцатидневный архив сводок и метаданных публикации. Повторная архивация может
обновлять только изменяемые эксплуатационные поля и никогда не заменяет
валидную сводку пустым значением.

#### `daily_lifecycle`

Защитный жизненный цикл дня для каждой группы.

Основные поля:

- `chat_id`;
- `summary_date`;
- количество сообщений и checksum или watermark;
- `summary_prepared_at`;
- `summary_sent_at`, допускает пустое значение при недостижении порога;
- `archive_completed_at`;
- число архивированных сообщений и результат проверки;
- `working_cleanup_completed_at`.

#### `job_locks`

Короткие блокировки-аренды для плановых и recovery-задач. Блокировка имеет
срок действия, поэтому аварийно завершившийся процесс не может остановить
систему навсегда.

#### `schema_migrations`

Версии и время применённых миграций.

## 5. Защита данных и сроки хранения

Главное правило: временные дубли допустимы, молчаливая потеря или случайное
перетирание данных — нет.

### 5.1 Защита updates и сообщений

- Webhook фиксирует `telegram_updates` до начала обработки.
- `update_id` не позволяет повторно выполнить один update.
- `(chat_id, telegram_message_id)` не позволяет повторно сохранить сообщение.
- Локальные изменения состояния одного update выполняются транзакционно.
- Зависший `processing` возвращается в `retry` после окончания аренды.
- При окончательной ошибке payload и сведения об ошибке сохраняются для
  диагностики в пределах срока хранения.

### 5.2 Защита сводок

- У плановых и ручных сводок разные идентичности.
- Ручная сводка никогда не перезаписывает плановую.
- Новая генерация создаёт новую запись или безопасный переход состояния.
  Пустой или ошибочный результат не заменяет существующую валидную сводку.
- Публикация выполняется через outbox с уникальным дневным ключом.
- Перед повторной отправкой проверяется текущее состояние публикации.

### 5.3 Последовательность архивации и очистки

Рабочие сообщения не перемещаются разрушительной операцией. Дневной цикл:

1. скопировать подходящие строки в архив идемпотентными вставками;
2. сравнить ожидаемые и архивные идентификаторы и количество сообщений;
3. установить `archive_completed_at`;
4. отдельной cleanup-задачей удалить рабочие строки только при выполнении
   защитных условий;
5. записать завершение очистки.

Если сообщений меньше автоматического порога, жизненный цикл фиксирует
намеренное отсутствие публикации и после проверки всё равно разрешает
архивацию и очистку.

Если публикация в Telegram, генерация Groq или проверка архива завершилась
ошибкой, рабочие сообщения остаются доступными для повторной попытки.

### 5.4 Сроки хранения

- рабочие сообщения — до подтверждённой архивации дня и безопасной очистки;
- архивные сообщения и сводки — 30 дней;
- payload updates и диагностика задач — 30 дней;
- MySQL backup — не более 30 дней;
- логи приложения — не более 30 дней с ротацией.

Удаление использует строгие условия вида `created_at < cutoff`, выполняется
ограниченными порциями и не входит в транзакцию архивации.

### 5.5 Backup и миграции

- MySQL backup выполняется дважды в сутки и непосредственно перед production-
  миграциями.
- Backup хранится вне `public_html`.
- Файлы старше 30 дней автоматически удаляются.
- Деплой никогда не загружает дамп поверх production-данных.
- Все изменения схемы оформляются версионными миграциями.
- Миграции `0.2.x` по возможности сохраняют совместимость с предыдущей версией
  приложения, чтобы код можно было откатить без отката базы.

## 6. Работа с LLM

### 6.1 Провайдер и модель

Основной провайдер — Groq Free API с включённым Zero Data Retention.

Начальная модель:

```text
qwen/qwen3.6-27b
```

Имя модели задаётся переменной `GROQ_MODEL` и не зашивается в бизнес-логику.

API-ключ провайдера хранится только в environment-файле на Beget.

### 6.2 Граница провайдера

Сервис суммаризации зависит от внутреннего интерфейса LLM-клиента, а не от
конкретных вызовов Groq. Реализация провайдера возвращает:

- сырой или структурированный ответ;
- название провайдера и модели;
- длительность;
- расход токенов, если он доступен;
- нормализованную категорию ошибки.

Благодаря этому Groq позднее можно заменить другим бесплатным или платным
провайдером без изменения сценария суммаризации.

### 6.3 Ограничение prompt и transcript

Сохраняются существующий структурированный формат русской сводки и
эвристические проверки качества.

Transcript ограничивается по токенам и символам. Если активная группа выходит
за лимит, сообщения сокращаются детерминированно с сохранением:

- хронологического покрытия;
- повторяющихся тем;
- указания участников;
- последних решений и незакрытых вопросов.

Первая реализация может использовать ограниченный набор последних сообщений и
детерминированную выборку. Рекурсивная многоступенчатая суммаризация не входит
в начальный объём, пока реальная нагрузка не покажет её необходимость.

### 6.4 Поведение при ошибках

- Для LLM-запросов устанавливаются явные connect и total timeouts.
- Повторные попытки ограничены и применяются только к временным ошибкам.
- При `429` учитывается `Retry-After`, если это совместимо с дедлайном запроса.
- Для некорректного структурированного ответа допускается один repair-запрос.
- После неудачных попыток существующий эвристический суммаризатор формирует
  пригодный результат.
- При приближении к установленным приложением бесплатным лимитам ручной запрос
  получает свежую кешированную или эвристическую сводку, а не ошибку.

Бесплатная квота не считается SLA. Продукт должен продолжать работать без
Groq.

### 6.5 Приватность и логи

- Transcript группы отправляется в Groq только для запрошенной генерации
  сводки.
- Пользователям сообщается, что сообщения обрабатываются внешним AI-сервисом.
- Полные transcript и ответы Groq не сохраняются в обычных логах.
- В логах остаются только технические метаданные: provider, model, duration,
  размер входа, статус, количество повторов и тип fallback.
- Токены и webhook secrets никогда не логируются.

## 7. Расписание

В часовом поясе Москвы через Beget CronTab запускаются:

- `*/5 * * * *` — восстановление ожидающих, повторяемых и зависших updates и
  summary jobs;
- `45 20 * * *` — подготовка плановых сводок;
- `0 21 * * *` — публикация подготовленных сводок;
- `15 21 * * *` — архивация и проверка завершённого дня;
- `30 21 * * *` — очистка рабочих строк, прошедших защитные условия;
- `50 11,23 * * *` — создание MySQL backup;
- `15 3 * * *` — удаление просроченного архива, диагностики, логов и backup;
- `0 9 * * *` — эксплуатационная проверка и уведомление владельца.

Неудачная плановая операция также сохраняется как повторяемое задание. Поэтому
recovery worker может завершить публикацию, архивацию или очистку после
номинального времени. Очистка разрешается состоянием данных, а не только
наступлением заданной минуты.

## 8. Безопасность

- Webhook принимает только `POST`.
- Telegram webhook secret проверяется до обработки payload.
- Некорректный запрос получает ошибку без раскрытия конфигурации.
- Команды настройки группы требуют подтверждённых прав администратора.
- Личная выдача сводки требует подтверждённого текущего членства.
- Callback содержит короткий непрозрачный идентификатор, а авторизация
  выполняется на сервере.
- Environment-файлы, backup, логи и миграционные реквизиты находятся вне web
  root.
- Для MySQL используется отдельный пользователь с доступом только к базе
  BrevitySisterBot.
- Production и preview используют разные боты, secrets, каталоги и базы.
- Исходные сообщения групп не включаются в обычные логи и служебные
  уведомления.

## 9. Наблюдаемость и эксплуатация

### 9.1 Health-check

Публичный health endpoint без секретов сообщает, может ли приложение
запуститься и подключиться к MySQL. Он не раскрывает credentials, payload
очереди, названия групп или тексты сообщений.

### 9.2 Ежедневная эксплуатационная проверка

Проверяются:

- количество `pending`, `processing`, `retry` и `failed`;
- возраст самого старого незавершённого update;
- просроченные job leases;
- плановые сводки, которые не были опубликованы;
- ошибки проверки архива;
- возраст и успешность последнего backup;
- частота недавних ошибок Groq и включения fallback.

При проблеме владельцу отправляется короткое служебное Telegram-уведомление без
пользовательского содержимого.

### 9.3 Логирование

Логи позволяют сопоставить:

- Telegram `update_id`;
- job ID;
- безопасно представленное значение `chat_id`;
- summary ID;
- категорию ошибки и номер попытки.

Полные тексты сообщений и секреты в логах отсутствуют.

## 10. Стратегия тестирования

### 10.1 Unit-тесты

Проверяются:

- пороги 5 и 15 сообщений;
- parsing, validation, repair и эвристический fallback сводки;
- ограничение transcript;
- права администраторов;
- текущее членство;
- выбор группы в личном чате;
- подавление повторной команды;
- условия архивации и очистки;
- расчёт сроков хранения.

### 10.2 Тесты repositories и миграций

Они выполняются на изолированной тестовой MySQL-базе и проверяют:

- уникальные ключи updates и сообщений;
- захват update и восстановление просроченной аренды;
- транзакционные переходы состояния;
- идемпотентность плановой публикации;
- копирование и проверку архива;
- защитные условия очистки;
- миграцию пустой базы `0.2.0`;
- импорт единственной живой группы `0.1.0`.

SQLite может оставаться в тестах только для проверки исторического поведения
внутри `mvp-1/`. Production repositories работают с MySQL.

### 10.3 Контрактные тесты

Telegram и Groq подменяются mock-ответами для следующих сценариев:

- повторная доставка webhook;
- Telegram timeout и безопасный retry;
- Groq timeout;
- `429` с `Retry-After` и без него;
- некорректный JSON;
- валидный структурированный ответ;
- удалённая или недоступная настроенная модель.

### 10.4 End-to-end и аварийные тесты

Проверяются:

- путь webhook → MySQL → processor → Telegram-ответ;
- сохранение сообщения группы без задержки сбора;
- личный `/summary` с одной и несколькими группами;
- завершение процесса и восстановление через пятиминутный cron;
- повторные плановые запуски без двойной публикации;
- сохранение рабочих данных при ошибке архива;
- эвристическая сводка при недоступности LLM.

### 10.5 Preview smoke-test

Перед production проверяется:

- webhook принимает правильный preview secret и отклоняет неправильный;
- включить preview-группу может только администратор;
- сообщения появляются только в preview-базе;
- групповой и личный `/summary` работают;
- выбор группы работает;
- плановая подготовка и публикация работают;
- проверка архива и очистка работают;
- backup создаётся вне web root;
- количество строк production-базы не меняется.

## 11. Структура репозитория и релиза

### 11.1 Сохранение MVP

Текущая реализация из корня репозитория сохраняется в каталоге:

```text
mvp-1/
```

Снимок содержит исходный код, тесты, документацию и примеры деплоя `0.1.0`,
необходимые для понимания или запуска MVP.

В committed snapshot не попадают:

- runtime secrets;
- виртуальные окружения;
- логи;
- созданные базы;
- локальные кеши;
- рабочие файлы визуализации.

При переносе в `mvp-1/` поведение старой версии не изменяется.

### 11.2 Новый корень

В корне размещается новое приложение `0.2.0` с ясными границами:

```text
app/
  config/
  domain/
  services/
  repositories/
  integrations/
    telegram/
    groq/
  web/
  jobs/
migrations/
scripts/
tests/
docs/
passenger_wsgi.py
pyproject.toml
```

Окончательные имена пакетов и детализация файлов определяются implementation
plan, но должны сохраняться следующие направления зависимостей:

- domain-код не импортирует Telegram, Groq, WSGI или MySQL drivers;
- services зависят от интерфейсов;
- repositories и integrations реализуют эти интерфейсы;
- webhook и cron-команды остаются тонкими точками входа.

### 11.3 Версионирование

- историческая реализация — `0.1.0`;
- первый релиз переписанной версии — `0.2.0`;
- версия схемы и версия приложения показываются независимо;
- релиз проходит через preview, smoke-test, release commit, tag и production-
  деплой.

## 12. Импорт и переключение

Сейчас живые данные есть только у одной группы `0.1.0`. Поэтому вместо общего
dual-write перехода используется контролируемый одноразовый импорт.

Импорт:

1. создаёт неизменяемые backup `bot.db` и `archive.db`;
2. читает настройки групп, рабочие сообщения, подготовленные сводки и архив;
3. записывает их в MySQL-таблицы `0.2.0` с идемпотентными ключами;
4. сравнивает количество строк и идентификаторы;
5. формирует отчёт об импорте;
6. не удаляет и не изменяет исходные SQLite-файлы.

Переключение:

1. развернуть и проверить preview с отдельным ботом;
2. развернуть production-код и мигрировать пустую production-схему;
3. выполнить и проверить одноразовый импорт;
4. остановить старый polling и старые задания сбора;
5. настроить production webhook;
6. проверить webhook info и живое сообщение в группе;
7. хранить SQLite backup не менее 30 дней стабилизации;
8. включить автоматическую очистку только после полного успешного дневного
   цикла.

Telegram long polling и webhook нельзя одновременно использовать для одного
production-бота.

## 13. Что не входит в `0.2.0`

- индивидуальное время публикации для групп;
- более одного часового пояса;
- web-панель администрирования;
- подписки и биллинг;
- векторный поиск и долговременная семантическая память;
- получение сводок старше 30-дневного архива;
- обработка нетекстовых media, кроме captions;
- Redis, RabbitMQ, Kafka и другие распределённые брокеры;
- multi-region и горизонтально масштабируемый runtime.

## 14. Критерии готовности

Релиз `0.2.0` готов, когда:

1. Telegram-сообщения немедленно сохраняются через webhook.
2. Повторные updates, jobs, imports и cron-запуски не создают дубли сообщений
   или плановых публикаций.
3. Прерывание процесса не может потерять зафиксированный update.
4. Рабочие сообщения никогда не удаляются до подтверждённого завершения
   архивации.
5. Groq `qwen/qwen3.6-27b` создаёт валидные русские сводки, а при недоступности
   включается детерминированный fallback.
6. Автоматическая сводка использует порог 15 сообщений и публикуется в 21:00
   по Москве.
7. Групповая и личная ручные сводки используют порог пять сообщений.
8. Личная сводка раскрывает данные только после проверки текущего членства.
9. Включать и отключать сводки могут только администраторы.
10. Архив, логи, диагностика updates и backup соблюдают максимальный срок
    хранения 30 дней.
11. Preview полностью изолирован от production.
12. Единственная живая MVP-группа импортируется с проверкой количества строк и
    идентификаторов.
13. Все автоматические тесты и preview smoke checklist проходят.
14. BernsBot продолжает независимо работать во время всего деплоя.
